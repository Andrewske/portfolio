Change data model so a track can exist in multiple buckets simultaneously.
- *Pro*: Accurately reflects reality, no special cases

**Option 2: Priority-based claiming**
First bucket (by order) that has a linked playlist containing the track "claims" it. Other buckets just don't show it.
- *Pro*: Minimal change, keeps single-bucket model
- *Con*: Arbitrary, user loses visibility into other memberships, bucket order suddenly matters

**Option 3: Primary bucket + membership badges**
Track lives in one bucket (user-assigned or first-match), but displays small badges/icons showing which other linked playlists it belongs to.
- *Pro*: Keeps simple model, adds visibility without complexity
- *Con*: Sync on removal becomes ambiguous - remove from all linked playlists or just the primary?

**Option 4: Outward-only sync**
Linked buckets push changes TO playlists (add/remove), but don't auto-populate FROM external playlist changes. Inverse sync disabled.
- *Pro*: Eliminates conflict entirely, simpler mental model
- *Con*: Loses the inverse-sync feature you described
