## Top 3 Solutions

### 1) Single Migration + Syncthing Propagation
- **Approach**: Stop local + piserver Docker, run migration locally only, let Syncthing propagate the changes to pi, restart both. The databases are already synced bidirectionally (`sendreceive`), so changes will automatically flow.
- **Pros**: Simplest workflow, no manual scp, leverages existing infrastructure, single source of truth
- **Cons**: Need to wait for Syncthing to sync before restarting piserver (~30s for 27MB), sync conflicts possible if timing is wrong
- **Effort**: S
- **Risk**: Low (databases already identical via Syncthing)

### 2) Single Migration + Manual SCP (Original Option 2)
- **Approach**: Stop both, run migration locally, manually scp database to pi, restart both. Bypasses Syncthing for this operation.
- **Pros**: Explicit control over timing, no waiting for sync propagation
- **Cons**: Redundant with existing Syncthing setup, could cause Syncthing conflict if not paused, extra manual step
- **Effort**: S
- **Risk**: Med (could conflict with Syncthing)

### 3) Dual Migration (Original Option 1)
- **Approach**: Stop both, run migration script on both machines independently, restart both.
- **Pros**: Each machine handles its own data
- **Cons**: Databases are already identical - running twice is redundant, risk of divergence if scripts differ slightly, more steps
- **Effort**: M
- **Risk**: Med (unnecessary complexity)

## Recommendation
- **Pick**: #1 (Single Migration + Syncthing Propagation)
- **Why this is best**:
  - Databases are **already identical** (same MD5 hash) - Syncthing is working
  - Running migration once and letting Syncthing propagate is the simplest path
  - Avoids manual scp that could conflict with Syncthing's own sync
  - Just need to wait ~30-60s after migration before restarting piserver to ensure sync completes
